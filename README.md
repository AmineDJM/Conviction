# Conviction — AI Venture Investment Partner

An institutional venture-capital underwriting and decision operating system. Upload a startup deck; Conviction reconstructs what the company actually does, extracts every material claim and metric, researches founders, claims, market and competitors, models ownership and venture returns, tries to falsify the thesis, and prepares the Quick Memo, the founder questions and the Investment Memo — all backed by an auditable evidence ledger.

A single global **Fund Brain** answers questions across every deck, memo, source and decision of the fund. It works like a partner who has read every deck and attended every IC.

> Quantify what can genuinely be quantified. Structure what cannot. Never manufacture certainty.

## Deploy on Render (the only thing to fill in: `OPENAI_API_KEY`)

1. Push this repository to GitHub.
2. In Render: **New → Blueprint** → select the repository. Render reads `render.yaml`.
3. When prompted, paste your **`OPENAI_API_KEY`**. Nothing else is required:
   - `SESSION_SECRET` is generated by Render.
   - The database (SQLite) and uploaded documents live on the persistent disk mounted at `/var/data`. No Supabase or other external database is needed.
4. Open the service URL. The first visit shows **Set up your workspace**: enter the fund name (e.g. VUVP), your name, email and password. That account owns the workspace.
5. Go to **Fund** → set the fund profile (mandate, check sizes, ownership target, return targets), then document strategy, criteria, verticals, IC members and their documented preferences.

Notes
- Render persistent disks require a paid instance (the blueprint uses `starter`) and a single instance (`numInstances: 1`). SQLite on the disk is the whole database; Render snapshots disks daily.
- Analyses run in the web process. A redeploy interrupts analyses in flight; they are marked *failed — interrupted* at startup (no fabricated results) and can be re-run.
- Health check: `GET /api/health`.

## Operations

Everything below works with the default blueprint: `OPENAI_API_KEY` is still the only value to fill in. `SESSION_SECRET` and `DATA_ENCRYPTION_KEY` are generated by Render; every other variable is optional. Owners manage all of this under **Settings** (`/settings`).

### Backups

- **What**: the SQLite database, via SQLite's online backup API (consistent while the app keeps writing). Each backup is opened read-only and must pass `PRAGMA integrity_check`; key table row counts and the migration version are recorded in a sidecar `.json`.
- **When**: daily (checked hourly by the server; a backup is taken when the newest daily one is 24 h old, so redeploys never skip a day), **automatically before database migrations** whenever an existing database has pending migrations (the migration is refused if that backup cannot be verified), and on demand (**Settings → Data & backups → Create backup now**, or `npx tsx scripts/backup.ts`). Backups cover the whole instance, so the backup list and the button are shown only to the owner of the first (setup) workspace; owners of other workspaces use their workspace export.
- **Where**: `BACKUP_DIR`, default `<dirname(DATABASE_PATH)>/backups` → `/var/data/backups` on Render, named `conviction-<iso-timestamp>.db`.
- **Retention**: the newest 14 daily, 10 manual and 10 pre-migration backups.
- **Off-site (optional)**: with object storage configured (below), every backup is also uploaded, encrypted (AES-256-GCM), to `backups/` in the bucket. Without it, backups sit on the same disk as the database: they protect against bad migrations, bugs and mistakes, not against losing the disk (Render's daily disk snapshots cover that case).
- `npx tsx scripts/backup.ts --list` lists local and remote backups. `BACKUP_SCHEDULE=off` disables the daily timer.

Uploaded documents are not in the database backup. They live on the disk or in object storage (see below), and a full export includes them.

### Restore

1. Open the Render **Shell** for the service (or a terminal with the same environment).
2. Choose a backup: `npx tsx scripts/backup.ts --list`.
3. Restore it over the live database:
   ```bash
   npx tsx scripts/restore.ts latest --force                      # or a file: /var/data/backups/conviction-2026-…Z.db
   npx tsx scripts/restore.ts --remote latest --force             # disk lost: download the newest off-site copy
   ```
   The backup is verified first (integrity check, key tables, decrypted when it is an off-site `.cve` copy). An existing database is **never** overwritten without `--force`. With `--force`, a verified copy of the current database is written next to it first (`conviction.db.pre-restore-<iso>.db`).
4. **Restart the service** right away from the Render dashboard so it opens the restored file. Anything written between the restore and the restart is lost.

To inspect a backup without touching production, restore it to another path: `npx tsx scripts/restore.ts <file> --target /tmp/inspect.db`.
The restore path has an automated test (`tests/infra.backup.test.ts`): it seeds a database, backs it up, restores it elsewhere and compares counts and rows.

### Export

**Settings → Data & backups → Export everything** (owners; `GET /api/admin/export`, `?files=0` leaves out the documents) returns one ZIP:
`manifest.json` (format, export time, migration version, row counts), `workspace.json`, `members.json` (no password hashes), `tables/*.json` for every workspace table (companies, versions, documents metadata, pages, runs, costs, history, fund knowledge, IC members and observations, meetings, chats, funds, memory packs, metric facts, entities, relations, chunks without embeddings, audit log) and `documents/…`, the original uploads **decrypted**. The export is built in memory with a size guard (`EXPORT_MAX_BYTES`, default 400 MB). Every export is written to the audit log.

### Encryption at rest

- Uploaded documents are encrypted before they are written, on disk or in object storage: AES-256-GCM with a random 12-byte IV per file, the auth tag appended, and a versioned `CVE1` header. The key is derived with HKDF-SHA256 from `DATA_ENCRYPTION_KEY`, which Render generates.
- If `DATA_ENCRYPTION_KEY` is missing in production, the key is derived from `SESSION_SECRET` and a warning is logged. Development uses a fixed development key. Files written before encryption existed (no header) are still read transparently.
- Key rotation: set the new `DATA_ENCRYPTION_KEY` and move the old value to `DATA_ENCRYPTION_KEY_PREVIOUS`. Reads try both, and new writes use the new key.
- **Keep a copy of `DATA_ENCRYPTION_KEY`** somewhere safe, such as your password manager. Without it, stored documents and off-site backups cannot be decrypted.
- The SQLite database, which holds extracted page text, is not encrypted by the application. It relies on the disk's own encryption at rest. Treat backups and exports as confidential.

### Object storage (optional)

Set these on the service to keep documents and off-site backups in any S3-compatible store: AWS S3, Cloudflare R2, Backblaze B2, MinIO or Supabase Storage's S3 endpoint. Requests use path-style URLs and SigV4, with no SDK.

| Variable | Required | Example |
|---|---|---|
| `S3_BUCKET` | yes | `conviction-prod` |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | yes | bucket-scoped key |
| `S3_ENDPOINT` | for non-AWS | `https://<account>.r2.cloudflarestorage.com` |
| `S3_REGION` | default `us-east-1` | `auto` (R2), `us-west-004` (B2) |
| `S3_PREFIX` | no | `conviction/` |

Object storage is used only when all three required variables are set. Documents uploaded earlier stay readable from the disk.

**Supabase Storage** (Supabase → Project settings → Storage → S3 connection): create a private bucket, generate an S3 access key, then set

| Variable | Value |
|---|---|
| `S3_ENDPOINT` | `https://<project-ref>.supabase.co/storage/v1/s3` |
| `S3_REGION` | your project's region, e.g. `eu-west-3` |
| `S3_BUCKET` | the bucket name |
| `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` | the generated S3 key |

Documents and off-site backups are then stored (encrypted by the application, AES-256-GCM) in Supabase; the SQLite database stays on the Render disk. Nothing else from Supabase is required.

### Integrations (optional): Zoom and Google Meet

The meetings workflow never needs an integration: a transcript can be pasted or uploaded (.txt, .md, .vtt, .srt) and a recording uploaded and transcribed. Connecting Zoom or Google Meet only adds **Import from Zoom / Google Meet** on a deal's Meetings tab. Setup is per server (client id + secret); each member then connects their **own** account under **Settings → Integrations**, which also shows the exact redirect URI to register and the scopes.

| Variable | Provider |
|---|---|
| `ZOOM_CLIENT_ID` / `ZOOM_CLIENT_SECRET` | Zoom General app (user-managed, OAuth) |
| `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` | Google Cloud OAuth client (Web application) |
| `APP_URL` | Public URL used to build the redirect URIs (default: Render's `RENDER_EXTERNAL_URL`, else the request's host) |

Redirect URIs: `<APP_URL>/api/integrations/zoom/callback` and `<APP_URL>/api/integrations/google_meet/callback`.

**Zoom** — Zoom App Marketplace → Develop → Build App → *General App*, user-managed. Add the redirect URI (and to the OAuth allow list) and the scopes `cloud_recording:read:list_user_recordings` (list your cloud recordings and their files) and `user:read:user` (show the connected account); classic apps use `recording:read` and `user:read`. Turn on *Cloud recording* and *Create audio transcript* in Zoom so recordings carry a VTT transcript. Import prefers that transcript (Zoom's speaker names and cue times, parsed exactly like an uploaded .vtt); without one, the audio file (M4A, else MP4) goes through the recording transcription path — the bundled ffmpeg converts it to 16 kHz mono WAV and it is split and diarized like any long recording (up to 200 MB per file). A development app can only be authorized by users of the developer's own Zoom account.

**Google Meet** — Google Cloud console: enable the *Google Meet REST API* and the *Google Drive API*; OAuth consent screen with the scopes below; Credentials → OAuth client ID → *Web application* with the redirect URI. Scopes, and why these are the minimal ones:
- `https://www.googleapis.com/auth/meetings.space.readonly` (sensitive) — conference records, participants, transcripts and **transcript entries** (Meet REST API v2). Entries are the primary source: one per utterance with the participant and exact start/end times; speaker names come from resolving each entry's participant (signed-in, anonymous or phone user).
- `https://www.googleapis.com/auth/drive.meet.readonly` (restricted) — only Drive files created or edited by Meet. Used solely as a fallback: Google keeps transcript entries 30 days after the meeting, after which the transcript Google Doc is exported as text (`files.export`, `text/plain`) — speaker names kept, only Meet's periodic timestamps. It is much narrower than `drive.readonly`; if the user does not grant it, recent meetings still import and older ones say why they cannot.
- `openid email` — to show which account is connected.
An *Internal* app (Google Workspace) needs no verification; an *External* app needs Google's verification for the sensitive and restricted scopes (Testing mode works for up to 100 listed test users). Meet only produces transcripts on Workspace editions with transcription, when it was turned on in the meeting.

Security: OAuth 2.0 authorization code with PKCE (S256) and a 256-bit `state` that is single-use, expires after 10 minutes and is bound to the workspace, user and browser session that started the flow (a callback from another session is rejected and audited). Return paths are same-origin relative paths only. Tokens are stored encrypted (AES-256-GCM, `DATA_ENCRYPTION_KEY`) per workspace member in `integration_connections`, are used only for that member's own listings and imports, never logged, exported or sent to the browser, and are deleted on **Disconnect** (after revoking at the provider) or when the member is removed. Access tokens are refreshed shortly before expiry and on any 401 (refresh → retry once); Zoom's rotating refresh token is replaced atomically and refreshes are single-flight. A rejected refresh marks the connection *Reconnect needed*. Download URLs are never taken from the browser (the server re-lists and resolves the file) and the bearer token is sent only to Zoom/Google hosts, never to a redirect target on another origin. Rate limits: a short `Retry-After` is retried once, a longer one is reported. Connect, reject, disconnect, listing and every import are in the audit log; viewers cannot connect or import.

Development without credentials: `npx tsx scripts/mock-integrations.ts` starts a local mock of the documented Zoom and Google endpoints (auto-consent, PKCE, token rotation, sample recordings and Meet transcripts); run the app with `CONVICTION_INTEGRATIONS_MOCK_URL=http://127.0.0.1:4020` and the printed client ids (ignored when `NODE_ENV=production`). `tests/integrations.zoom.test.ts` and `tests/integrations.google.test.ts` run against it.

### Integrity checks

`GET /api/admin/consistency` (owners and partners), also shown under **Settings → Data & backups**, verifies that every company's pipeline projection, metric facts, deal memory and retrieval chunks match its current version.
`npx tsx scripts/load-test.ts --n 20` runs N concurrent analyses against a local mock of the OpenAI API (`scripts/mock-openai.ts`, which is also usable for offline development through `OPENAI_BASE_URL`). It reports latency, SQLite lock errors, duplicate rows and consistency.

## What it does

- **Upload → analysis**: PDF, PPTX, images, several documents; three depth modes: Fast screen (≈ $0.03–0.08, hard cap $0.15), Standard (target ≤ $0.25, hard cap $0.50 enforced in code), Deep DD (explicit budget). Real progress steps, and a preliminary understanding appears before the full analysis finishes.
- **Decision cockpit**: plain-language explanation; Operating Quality (index with bounds and coverage, peer-relative), Evidence (anchored category), Power-law potential, Fund fit (binary mandate gates plus a descriptive index), Risk (multidimensional); exceptional strength; the bet; what could break it; core metrics with evidence labels; next best action; recommendation gates.
- **Tabs**: Quick Memo (one printable page, focus mode) · Product (before/after) · Founders (capabilities, not pedigree) · Market (reconstructed bottom-up, value capture, top-down; deck TAM never accepted) · Traction · GTM · Economics (every metric traced to definition and formula) · Competition (incumbent-copy, cost-commoditization and distribution tests; moat dynamics) · Returns (interactive model, backwards return, price sensitivity, financing path with delay scenarios) · Risks (repairable / structural / thesis-killing, falsification, symmetric red team) · Evidence (claim ledger with source extracts) · Questions (decision-tested, founder-call update) · Reports (Investment Memo, Founder Call Brief) · History (versions and diffs).
- **Compare, IC, Portfolio, Benchmarks** (registry inspector + *Recalculate portfolio* with version-preserving re-scoring), **Fund** (profile, documented knowledge, IC members, meeting transcripts → observed statements).
- **Fund Brain** (⌘J anywhere): hybrid retrieval over structured facts, memory packs, FTS5, embeddings and the entity graph; answers stream with clickable citations and labels (verified / company-reported / inferred / estimate / unknown), and it says *we don't know yet* when the records are silent.
